# MdToLaTeX (Markdown to LaTeX & PDF Editor)

VS Code 風の操作感を備えた、**Markdown と LaTeX のリアルタイム双方向編集が可能なブラウザ完結型 PDF エディター**です。

理系文書・教材・論文・指導案などの作成に特化し、数式パレット、Mafs / TikZ によるグラフ・図形描画、Word 風テーブル挿入、コールアウト枠（定理・定義・命題など）の自動変換、Cloud LaTeX / Overleaf 互換の LaTeX コード出力をサポートしています。

---

## 1. プロジェクト概要

### 1.1 これがどのようなものなのか
Markdown の「手軽で素早い執筆体験」と、LaTeX の「美しく厳密な組版・数式表現」をシームレスに融合させた Web アプリケーションです。

- **ブラウザ完結（サーバーレス）**: すべての変換処理・状態管理はブラウザ上で動作。編集データはブラウザ内の IndexedDB に自動永続化されます。
- **3ペイン UI**:
  1. **左ペイン**: ワークスペース（ファイルツリー管理、新規作成/削除/リネーム/複製、テンプレート選択）
  2. **中央ペイン**: Markdown エディター（左）と LaTeX エディター（右）の 2 分割（比率変更可、Monaco Editor 搭載）
  3. **右ペイン**: リアルタイム プレビュー（KaTeX / Mafs ベースの高速描画、ページめくり、目次ジャンプ、全画面/別ウィンドウ表示、PDF エクスポート）
- **Cloud LaTeX / Overleaf 互換重視**: 生成された LaTeX コードをコピー＆ペーストするだけで、Cloud LaTeX や Overleaf（LuaLaTeX / upLaTeX / pdfLaTeX）でもエラーやレイアウト崩れなく即座にコンパイル可能です。

### 1.2 主な機能
- **Markdown ⇔ LaTeX 双方向リアルタイム同期**: 片方を編集すると他方が自動更新（ソース・オブ・トゥルース管理）。
- **理系文書向け拡張記法**:
  - 定理・定義・命題・証明などのコールアウト（`> [!定理 (1.1)]` ⇔ `\begin{定理}[定理 (1.1)]`）
  - 数式参照（`\label{eq:1}` / `\eqref{eq:1}`）
  - 複数行数式、cases、aligned、subequations 等のスマート相互変換
- **数式入力パレット (Math Palette)**:
  - 大学数学・物理・工学レベル（微積分、線形代数、集合論、ギリシャ文字、極限、矢印など）をワンクリックで挿入。カーソル位置追従機能付き。
- **数学グラフ・図形描画機能 (Mafs & TikZ)**:
  - 単位円、1次・2次・3次関数、三角関数（$\tan$ 含む不連続関数の漸近線分割出力対応）、平面ベクトル、幾何図形を GUI で設定・プレビューし、TikZ / PGFPlots コードとして出力。
- **Word 風テーブル作成 (Table Grid Picker)**:
  - 10×10 のグリッドをホバーして直感的に行・列を指定。
  - 学術論文向け（`booktabs`: toprule / midrule / bottomrule）や指導案向け（`tabularx` 全枠線）のスタイルに対応。
- **仮想ターミナル**:
  - `ls`, `cd`, `mkdir`, `mv`, `cp`, `rm`, `history` などの Linux コマンドでファイル操作が可能。
- **ダークモード / ライトモード対応**:
  - エディター・UI は好みのテーマを選択可能（PDF プレビューは LaTeX の指定カラーを忠実に出力）。

### 1.3 技術スタック
| 分類 | 採用技術 |
| :--- | :--- |
| **フレームワーク** | React 19, TypeScript, Vite |
| **スタイリング** | Tailwind CSS v4, Lucide React (アイコン) |

| **設定・メタ構文** | YAML (`yaml`) |
| **リンター** | Oxlint (`oxlint`) |

## 3. 仕様・要件定義の構造と開発フロー

本プロジェクトでは、機能ごとに独立した要件定義書が作成されており、タスクの進捗は `ToDo.md` で一元管理されています。

### 3.1 要件定義書一覧
開発や修正を行う際は、該当する機能の要件定義書を必ず参照してください。

1. [要件定義書.md](./要件定義書.md): システム全体のアーキテクチャ、双方向同期の基本原則、IndexedDB 永続化。
2. [要件定義書_CloudLaTeX互換性.md](./要件定義書_CloudLaTeX互換性.md): Cloud LaTeX / Overleaf 向けの余白設定、`tcolorbox` 余白、数式ブロック変換の一律化要件。
3. [要件定義書_グラフ・図形描画機能.md](./要件定義書_グラフ・図形描画機能.md): 単位円・関数グラフ・ベクトル・幾何図形の仕様と Mafs / TikZ 出力要件。
4. [要件定義書_数式パレット機能.md](./要件定義書_数式パレット機能.md): パレットの表示制御（スマートモード）、カテゴリ別テンプレート定義。
5. [要件定義書_テーブル入力機能.md](./要件定義書_テーブル入力機能.md): Word 風グリッドピッカー、クリーンテンプレート、booktabs / tabularx 仕様。
6. [要件定義書_変換拡張.md](./要件定義書_変換拡張.md): Description リストや特殊記法への対応方針。
7. [要件定義書_バグ報告機能.md](./要件定義書_バグ報告機能.md): フィードバック受付・環境情報収集・GitHub Issues 連携。

### 3.2 開発・タスク進行の手順
どのようなモデルや開発者であっても、以下のルールに従って作業を進めます：

1. **ブランチの確認**:
   - 原則として `feature/ai-agent-dev` または指定された作業ブランチで開発します。
2. **`ToDo.md` の確認**:
   - `ToDo.md` を開き、未着手（チェックが入っていない `- [ ]`）の項目を上から順に 1 つずつ着手します。
3. **要件定義書の参照**:
   - 実装内容に関連する `要件定義書_*.md` を確認し、設計方針やエッジケース（例外条件）を把握します。
4. **実装と局所編集**:
   - 既存の他の機能にデグレ（破壊的影響）が出ないよう細心の注意を払ってコードを変更します。
5. **ビルドテストの実行**:
   - `npm run build` を実行し、TypeScript のコンパイルエラーおよび Vite ビルドエラーがないことを確認します。
6. **チェックリストの更新と報告**:
   - 実装が完了したら `ToDo.md` の該当項目にチェック（`- [x]`）を入れ、変更内容と影響範囲をユーザーに報告します。

## 4. 開発時の重要な注意点・設計方針

他のモデルや無料プラン（トークン制限やコンテキスト幅が厳しい環境）で作業する際、**特に壊しやすく・注意すべきポイント**をまとめます。

### 4.1 双方向変換エンジン (`src/utils/converter.ts`) の注意点
- **「ソース・オブ・トゥルース（信頼できる情報源）」の厳守**:
  - Markdown と LaTeX の両方を編集可能なため、**「ユーザーが直前にどちらのエディタを触ったか」**を追跡し、アクティブなエディタから逆側のエディタへ変換・更新を行います。
  - 無限ループ更新（MD更新 → LaTeX更新 → 再びMD更新...）を防止するため、更新フラグやデバウンス処理が組み込まれています。ここを壊さないでください。
- **LaTeX 側でレイアウトを修正した場合の Markdown への補完・同期（バックプロパゲーション）**:
  - **プリアンブル・カスタム設定の保持 (`customPreamble`)**:
    ユーザーが LaTeX 側でパッケージ追加（`\usepackage`）、コマンド定義（`\newcommand`）、ボックススタイル（`\newtcolorbox`）、レイアウト・余白等のプリアンブル設定を直接変更した場合、標準テンプレートとの差分が `extractLaTeXMetadata` により自動抽出され、Markdown 側の YAML フロントマター（`customPreamble: |` や `md2latex:` 名前空間）へ自動補完・記録されます。この差分抽出ロジックを改変・破損すると、次回 Markdown 側を編集した瞬間にユーザーが LaTeX 側で調整したレイアウト設定が消失（上書きリセット）してしまうため、細心の注意を払ってください。
  - **本文内の詳細レイアウト・環境の透過的同期**:
    LaTeX 側で記述された複雑な数式環境（`subequations`, `align`, `cases`, `array`）、表構造（`booktabs`, `tabularx`）、TikZ 図形、コールアウト（`tcolorbox`）、詳細なラベル・参照などは、Markdown への逆変換時にも構文エラーを出さず、対応する Markdown 記法またはコードブロック（```tikz 等）として正しく保持・補完されます。
  - **情報の不可逆損失（ロスト）の防止**:
    「LaTeX 側で行ったレイアウトの微調整」が「Markdown 側のシンプルな記法」へ逆変換される際に削ぎ落とされないよう、`latexToMarkdown` を修正する際は、双方向のラウンドトリップ（MD → LaTeX → MD → LaTeX）を行ってもレイアウトや設定情報が欠落しないかを必ず検証してください。
- **数式ブロックの一律化ルール**:
  - Markdown の `$$ ... $$` は、原則として一律で `\begin{equation} ... \end{equation}` に変換します。
  - ユーザーが手動で `\begin{align}` や `\begin{cases}` などを書いた場合は、勝手に書き換えずにそのまま透過させます。
- **コールアウト記法と LaTeX 環境の対応**:
  - `> [!定理 (1.6) ロルの定理]` のようにタイトルや番号が付与されている場合、ベース名（定理）を抽出し、`\begin{定理}[定理 (1.6) ロルの定理] ... \end{定理}` のように引数付き環境として正しく相互変換します。
- **空行・改行の扱い**:
  - Markdown の改行を安易に LaTeX の `\\` に変換すると、Cloud LaTeX で段落余白の計算が崩れます。段落の区切りには空行（`\par` 相当）を使用します。

### 4.2 Cloud LaTeX / Overleaf 互換性の維持
- **Web プレビューと TeX エンジンの挙動差**:
  - Web 上の KaTeX や SVG は寛容に描画されますが、実際の TeX コンパイラ（LuaLaTeX / upLaTeX / pdfTeX）は厳格です。
  - **不連続関数（$\tan x$ 等）のプロット**: PGFPlots は不連続点を跨いで直線を繋いでしまうため、漸近線ごとに `\addplot` を分割出力するロジック（`src/utils/tikzGenerator.ts` 内）を維持してください。
  - **余白・重なり問題**: `tcolorbox` のタイトルが本文と重ならないよう、適切なパディングとスキップ値（`before skip=1.5em`、`top=12pt` 等）を保ってください。

### 4.3 `src/App.tsx` の編集方針
- `App.tsx` は UI、ステート、エディタ設定、ショートカット、モーダル制御、ターミナルなど多くのロジックを含む大規模ファイルです。
- **ファイル全体の再生成は絶対に避ける**:
  - トークン枯渇や予期せぬコード脱落の原因になります。必要な関数・フック・JSX の該当ブロックのみをピンポイントで修正（部分置換）してください。

### 4.4 永続化（IndexedDB）の保護
- 編集中の Markdown / LaTeX ソース、作成したファイル群、選択中テンプレート、UI 状態は IndexedDB に保存されます。
- ファイルの追加、リネーム、削除、コピーを行う際は、IndexedDB のデータと React の状態が常に整合性を保つように実装してください。

## 5. 環境構築とコマンド

### 5.1 前提環境
- Node.js: 18.x 以上推奨
- パッケージマネージャー: npm

### 5.2 コマンド一覧
```bash
# 依存パッケージのインストール
npm install

# 開発サーバーの起動（Vite）
npm run dev

# 型チェック & プロダクションビルド（必ず修正後に実行）
npm run build

# リンター実行（Oxlint）
npm run lint

# ビルド成果物のローカルプレビュー
npm run preview
```

### 5.3 GitHub Pages への公開
- GitHub の **Settings → Pages → Build and deployment → Source** を **GitHub Actions** に設定してください。
- `.github/workflows/deploy-pages.yml` が `main` への push 時に Vite のビルドを実行し、生成された `dist` 全体（`index.html` と `assets`）を Pages に公開します。
- リポジトリ直下の `index.html` は Vite の開発用エントリーポイントです。Pages の公開元にリポジトリ直下を指定すると、ビルド済みアセットが揃わず表示できません。
- `dist/index.html` はハッシュ付き JS/CSS を参照するため、HTMLだけを個別にコピー・公開しないでください。Actions は毎回 HTML と対応するアセットをまとめて生成・公開します。

## 6. AI モデル（無料プラン / 他モデル）向け作業指示テンプレート

AI に新しい機能追加やバグ修正を依頼する際は、以下のプロンプト形式を使うと失敗を防げます：

```markdown
【対象ファイル】
- `src/utils/converter.ts` (または関連ファイル)
- `ToDo.md`

【依頼内容】
`ToDo.md` に記載されている未完了タスク「[ここにToDoの項目名を記述]」を実装してください。

【制約・注意事項】
1. 他の既存機能や既存の変換ルールに影響を与えないよう局所的に修正してください。
2. Cloud LaTeX / Overleaf 互換性を損なわない構文を出力してください。
3. `App.tsx` を修正する場合は、全体を書き直さず該当箇所のみを部分置換してください。
4. 修正後は必ず `npm run build` でコンパイルエラーがないことを確認してください。
5. 完了後、`ToDo.md` の該当項目をチェック済みにし、変更内容を簡潔に報告してください。
```
